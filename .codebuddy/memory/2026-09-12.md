## REST 页 SSE 实时流式适配（需求确认完毕，开工）

- 起因：用户在 Rest 页调 LLM（`stream: true`），响应是裸 SSE 文本，想要 Apifox 式的时间线视图。
- 现状调查结论：
  - 全仓库无 `text/event-stream` 处理；lens 机制在 `helpers/lenses/lenses.ts`（content-type 驱动 + body 嗅探先例 `isValidJSONResponse`）。
  - 桌面请求链路：`createRESTNetworkRequestStream`（helpers/network.ts，BehaviorSubject 先发 loading）→ KernelInterceptorService（desktop=NativeKernelInterceptorService，`platform/std/kernel-interceptors/native/`）→ common `~/kernel/relay` → `@hoppscotch/plugin-relay`（guest-js）→ tauri-plugin-relay → relay crate（**libcurl**，`transfer.rs` 的 `write_function` 已逐 chunk 回调只是聚合）。
  - kernel `RelayRequestEvents` 已定义 progress/stateChange 等事件，desktop impl 的 emitter 是空壳（预留口）。
  - 实时页 sse.vue 用原生 EventSource（GET-only，无 headers/auth），与 REST 流式无关，不可复用。
- 用户确认的需求：
  1. **实时流式渲染**（接受改 Rust/kernel 层），仅桌面 native 通道。
  2. 仅标准 SSE（W3C：data:/event:/id:/多行合并/注释行，识别 `[DONE]`）。
  3. 时间线 Tab 两模式：**分条展示**（每条一行 JSON 预览 + 时间戳，点击下方看完整 JSON Pretty/Hexdump/Raw）+ **自动合并**（delta 拼接）。
  4. **思考过程开关**（reasoning 单独分区显示在正文前）。
  5. 消息格式预设：OpenAI（content + reasoning_content/reasoning）/ Gemini / Claude / Ollama Generate / Ollama Chat / 自定义 JSONPath；**配置全局记住**。
  6. 只做 REST 页；历史/存档语义不变（收完存完整 body，时间线为派生视图）。
- 分层方案：Rust write_function 推 chunk → Tauri Channel → kernel emitter `chunk` 事件 → native interceptor → network stream loading 期间增量 next() → SSE lens 实时渲染。

## 流式不生效的根因与修复（当日第三轮）

用户实测：SSE 只在请求完成后一次性展示。靠应用日志 `~/Library/Logs/io.hoppscotch.desktop/io.hoppscotch.desktop.log`（DEBUG 级，含 curl debug + relay 事件）定位到链路，共两处阻断：

1. **前端 emitter 竞态（根因）**：`platform/std/kernel-interceptors/native/index.ts` 的 `ExecutionResult.emitter` 是懒 getter（`relayExecution?.emitter`），而 `helpers/network.ts` 的 `attachStreamingRelayEvents` 在 `execute()` 返回后一两个微任务内就同步读取 —— 那时 `executeRequest` 才走到第一个 await（cookie jar / `relayRequestToNativeAdapter`），`Relay.execute` 尚未执行 → emitter 恒为 `undefined` → 零订阅。修复：interceptor 内改为**同步创建**的 `RelayEventHub`，`bindRelayExecution` 把 relay 真实 emitter 的 `headersReceived`/`chunk` 转发进这个 hub。
2. **响应区渲染门槛（根因）**：`components/http/Response.vue` 的 `v-if="!loading && hasResponse"` 在 loading 期间完全不渲染 `LensesResponseBodyRenderer`。修复：新增 `hasStreamingResponse`（loading && streaming）与 `showLenses = hasStreamingResponse || (hasResponse && !loading)`。

无需改动的（已核对）：`components/http/Request.vue` 的 Send 路径 `subscribeToStream` 不过滤 loading 态（`updateRESTResponse` 直接写 doc）；Rust `transfer.rs` 的 content-type 门正常命中（用户响应头是 `text/event-stream; charset=utf-8`；libcurl 官方文档确认头部结束的空行会回调给 header_function）；JS 侧 `Channel` 载荷/顺序（@tauri-apps/api 2.1.1）与 `WireStreamEvent` 一致。

验证：eslint ✓、`node type-check.mjs` ✓、prepare-web + build:full ✓（12:4x 产物同路径）。

**教训**：桌面端跨层流式链路必须用运行日志验证；诊断入口 = 应用日志（DEBUG）+ 自检清单（Rust 是否武装 → JS 是否订阅 → UI 是否渲染）。

## 流式彻底失效的真正根因（当日第四轮）：Tauri Channel 协议版本错配

前一轮修掉 emitter 竞态 + Response 渲染门槛后用户实测仍无流式，且确认运行的就是最新构建（用 `$TMPDIR/hopp_bundle.zip` 与 `packages/hoppscotch-desktop/bundle.zip` 逐条目 diff 完全一致；并用 bundle 内 sourcemap 确认修复代码确实被打包）。

铁证根因：
- 应用打包的是 `@tauri-apps/api@2.1.1`（kernel 的 optional peerDependency，实际由 common/desktop 提供），它的 `Channel` 从回调参数里读 `{ id }` 当消息序号；
- Rust 端 tauri 2.10.3（`src/ipc/channel.rs`）投递的是 `{ message, index }`（直接 eval 与大 payload 的 fetch 路径都是这个形状）；
- 于是 `id === undefined`，每条消息被塞进 `pendingMessages["undefined"]` 后**永不投递**，且不报错 —— 整条流式侧信道静默失效。

修复（低侵入，不动依赖版本）：`hoppscotch-kernel/src/relay/impl/desktop/v/1.ts` 弃用 SDK 的 `Channel`，改为用 `transformCallback` 自注册回调 + 直接把 `__CHANNEL__:<id>` 标记字符串传给 `invoke`（Rust 的 `Channel::CommandArg` 正是解析该字符串），并按 `index` 做有序投递（>8KB 的 payload 走 fetch 往返，可能乱序）。顺带删掉该文件里未使用的 `decodeBase64`（原本就 lint 报错）。

验证：kernel `pnpm run lint` ✓、`tsc --noEmit` ✓、kernel dist 重建 ✓（dist 内可见 `__CHANNEL__:${...}` 与 `typeof s.index` 检查）、重建 webapp（新 chunk `index-CBP4jr9K.js`）后用 sourcemap 复核 bundle 内的 kernel dist 已是新实现 ✓、`build:full` ✓（DMG 首次失败是残留挂载卷 `/Volumes/dmg.Rm6iAS` 占用，重跑即成功）。
产物：`.../bundle/macos/Hoppscotch.app`、`.../bundle/dmg/Hoppscotch_1.0.0_aarch64.dmg`。

长期提醒：`@tauri-apps/api`（JS）与 `tauri`（Rust）**必须协议匹配**。本仓库把 JS SDK 钉在 2.1.1、Rust 却是 2.10.3，属于错配；将来升级 SDK 后这段 workaround 可以回退成直接用 `Channel`。
